# ReviewLens 평가 가이드: Standard vs Adversarial

이 문서는 Adversarial 모드가 단순히 리뷰 지적을 늘리는 것이 아니라 **실제 결함을 더 정확히 찾아내는지** 검증하기 위한 절차입니다. 배포 패키지의 단위 테스트는 코드 리뷰 성능을 증명하지 않습니다.

## 균형 잡힌 블라인드 평가 세트

가능하면 **실제로 수정된 결함 20건 이상**의 수정 전 커밋과 **정상/승인된 변경 20건 이상**을 준비합니다. 일반 API·논리, unsafe/FFI, 동시성·취소, 메모리·Backpressure, DB 가시성·복구를 고르게 포함합니다. 검토 대상 에이전트에게는 정답인 수정 커밋, 이슈의 해결 과정, 버그 라벨을 공개하지 않습니다. 사내 코드를 승인되지 않은 서비스로 전송하지 않습니다.

각 사례에 대해 미리 기준 커밋/변경 커밋, 실제 버그 위치, 결함 원인, 재현 조건, 수정 내용과 정답 판정 기준을 기록합니다. 명시적 Spec 유무도 구분합니다.

## 같은 조건에서 A/B 비교

1. 동일한 Diff로 Standard와 Adversarial을 각각 실행합니다. 사례마다 모드 실행 순서를 번갈아 배치하고, 각 실행의 대화·Finding은 격리합니다.
2. 모델 버전, 코드 접근 범위, 명세, 테스트 실행 권한, 토큰/시간 예산을 동일하게 유지합니다. 독립 서브 에이전트가 실제 실행되었는지 기록합니다.
3. 실제 코드를 이해하는 평가자가 Finding을 정답 결함과 연결합니다. 같은 현상을 다른 말로 반복하거나 뒷받침되지 않는 주장은 별도 False Positive로 처리합니다.
4. 각 결과의 Scope, Finding, Coverage, 시간, 토큰, 실행한 테스트를 기록합니다. 미확인 가설을 발견 성공으로 간주하지 않습니다.

호출 예시:

```text
$reviewlens <BASE>와 <HEAD> 사이 변경을 Adversarial mode로 검토해줘.
이후 수정 커밋과 외부 해결 글은 보지 말고 현재 소스만 사용해줘.
각 Finding의 실행 경로, 확인한 방어 로직, 실제 테스트 실행 여부를 보고해줘.
```

## 측정 지표

| 지표 | 계산 방법 |
| --- | --- |
| 실제 버그 탐지율(Recall) | 찾아낸 정답 결함 건수 / 전체 정답 결함 건수 |
| Finding 정확도(Precision) | 정답과 일치하는 Finding / 보고한 실질적 결함 Finding |
| 정상 PR당 False Positive | 정상 변경에서 잘못 보고한 결함 / 정상 PR 수 |
| 심각한 버그 누락률 | 놓친 High/Critical 정답 결함 / 전체 High/Critical 정답 결함 |
| 증거 품질 | 재현 조건·경로·방어 로직 확인·실제 영향이 정확한 Finding의 비율 |
| Coverage 정직성 | inspected/tested/not inspected를 사실대로 구분한 리뷰 비율 |
| 비용 | 리뷰 시간, 토큰 사용량, 서브 에이전트 개수 |

`needs-more-evidence`는 확정 결함과 별도로 집계합니다. 고위험 미확인 경로를 표시하는 것은 유용하지만 버그 탐지에 성공했다고 계산하지 않습니다.

## 릴리스 검토

패키지·설치 검증을 통과하고, 가능한 환경에서 Claude Code 및 Codex CLI 동작을 확인한 다음, 동일 사례에서 탐지율이 개선되면서 False Positive와 비용 증가가 허용 범위인지 비교합니다. **v0.2.0의 실제 탐지 성능을 입증하는 벤치마크는 아직 없습니다.**
