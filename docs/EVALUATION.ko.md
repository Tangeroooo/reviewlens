# ReviewLens 평가 가이드: Standard vs Adversarial

이 문서는 Adversarial 모드가 단순히 리뷰 지적을 늘리는 것이 아니라 **실제 결함을 더 정확히 찾아내는지** 검증하기 위한 절차입니다. 배포 패키지의 단위 테스트는 코드 리뷰 성능을 증명하지 않습니다.

## 균형 잡힌 블라인드 평가 세트

가능하면 **실제로 수정된 결함 20건 이상**의 수정 전 커밋과 **정상/승인된 변경 20건 이상**을 준비합니다. 공개 계약, 경계 입력, 오류 동작, 재사용, 패키지 의존 방향을 포함합니다. 전문 렌즈를 평가할 때는 해당 분야 사례를 추가합니다. 검토 대상 에이전트에게는 정답인 수정 커밋, 이슈의 해결 과정, 버그 라벨을 공개하지 않습니다. 사내 코드를 승인되지 않은 서비스로 전송하지 않습니다.

각 사례에 대해 미리 기준 커밋/변경 커밋, 실제 버그 위치, 결함 원인, 재현 조건, 수정 내용과 정답 판정 기준을 기록합니다. 명시적 Spec 유무도 구분합니다.

## 영향 범위, 재사용, 패키지 구조의 평가 사례

각 쌍의 두 변경을 독립적으로 리뷰합니다. 리뷰어에게는 정답과 짝이 되는 변경을 보여주지 않습니다. 같은 범위와 예산에서 기본 리뷰, Standard, Adversarial의 결과를 비교합니다. 사례는 언어에 맞게 구현할 수 있습니다.

| 사례 | 문제가 있는 변경 | 대조 사례 | 판정 기준 |
| --- | --- | --- | --- |
| 소비자와의 계약 | API가 계약에 명시된 누락 표시값 대신 빈 값을 반환합니다. 변경되지 않은 소비자가 기본값 처리 경로를 건너뜁니다. | 내부 표현은 바뀌지만 어댑터가 공개 API의 누락 표시값을 보존합니다. | 소비자까지 영향을 추적하고 대조 사례에서 어댑터의 동작을 확인합니다. |
| 중복 검증 | 두 진입점이 기존 공통 검증의 상한 규칙을 다시 구현합니다. 한쪽에서 상한과 정확히 같은 값을 거부합니다. | 두 경로 모두 공통 검증을 호출하고 한 경로에는 명세에 따른 별도 전제조건이 있습니다. | 경계 입력, 새 구현 두 곳, 기존 검증 위치를 연결합니다. 대조 사례의 별도 전제조건을 보존합니다. |
| 의존 방향 | 공용 패키지가 순수 변환 함수를 호출하려고 저장소 지침에 어긋나는 애플리케이션 패키지 의존을 추가합니다. 양쪽은 이미 변환 대상 타입을 소유한 패키지에 의존합니다. | 두 어댑터의 변환 코드가 유사해도 반올림 계약이 다르고 공유해야 할 정책이 없습니다. | 첫 사례에서 실제 의존 관계와 위반한 지침을 제시하고, 대조 사례에서 추출을 제안하기 전에 계약 차이를 확인합니다. |

확인된 결함, 적용 가능한 설계 제안, 대조 사례의 오탐, 확인한 패키지 간 경로, 시간과 토큰 비용을 기록합니다. 최종 리뷰에서 추가하거나 기각한 지적은 독립 평가자가 그 판단을 지지하는지 별도로 집계합니다.

## 같은 조건에서 비교

1. 동일한 Diff로 스킬 없는 기본 리뷰, Standard, Adversarial을 각각 실행합니다. 사례마다 모드 실행 순서를 번갈아 배치하고, 각 실행의 대화·Finding은 격리합니다.
2. 모델 버전, 코드 접근 범위, 명세, 테스트 실행 권한, 토큰/시간 예산을 동일하게 유지합니다. 독립 서브 에이전트가 실제 실행되었는지 기록합니다.
3. 실제 코드를 이해하는 평가자가 Finding을 정답 결함과 연결합니다. 같은 현상을 다른 말로 반복하거나 뒷받침되지 않는 주장은 별도 False Positive로 처리합니다.
4. 각 결과의 Scope, Finding, Coverage, 시간, 토큰, 실행한 테스트를 기록합니다. 미확인 가설을 발견 성공으로 간주하지 않습니다.

호출 예시:

```text
$reviewlens <BASE>와 <HEAD> 사이 변경을 Adversarial mode로 검토해줘.
이후 수정 커밋과 외부 해결 글은 보지 말고 현재 소스만 사용해줘.
각 Finding의 실행 경로, 확인한 방어 로직, 실제 테스트 실행 여부를 보고해줘.
```

## 측정 지표

| 지표 | 계산 방법 |
| --- | --- |
| 실제 버그 탐지율(Recall) | 찾아낸 정답 결함 건수 / 전체 정답 결함 건수 |
| Finding 정확도(Precision) | 정답과 일치하는 Finding / 보고한 실질적 결함 Finding |
| 정상 PR당 False Positive | 정상 변경에서 잘못 보고한 결함 / 정상 PR 수 |
| 심각한 버그 누락률 | 놓친 High/Critical 정답 결함 / 전체 High/Critical 정답 결함 |
| 증거 품질 | 재현 조건·경로·방어 로직 확인·실제 영향이 정확한 Finding의 비율 |
| Coverage 정직성 | inspected/tested/not inspected를 사실대로 구분한 리뷰 비율 |
| 비용 | 리뷰 시간, 토큰 사용량, 서브 에이전트 개수 |

`needs-more-evidence`는 확정 결함과 별도로 집계합니다. 고위험 미확인 경로를 표시하는 것은 유용하지만 버그 탐지에 성공했다고 계산하지 않습니다.

## 릴리스 검토

패키지·설치 검증을 통과하고, 가능한 환경에서 Claude Code 및 Codex CLI 동작을 확인한 다음, 동일 사례에서 탐지율이 개선되면서 False Positive와 비용 증가가 허용 범위인지 비교합니다. 평가 사례 설계와 실제 측정 결과를 구분합니다.
